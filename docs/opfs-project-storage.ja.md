# OPFS 作品ストレージ（草案 v0.1）

- 対象: TurboWarp-Plus-Editor の保存方式の追加
- 状態: 草案（未実装）。決定事項は「決定」、仮置きは「仮定」と明記する
- 配置: 実装は turbowarp-plus family の新パッケージ（MPL-2.0）。本リポジトリは設定 UI と port の結線のみ
- パッケージ名（仮）: `@kubohiroya/turbowarp-plus-editor-opfs-project`

## 1. 目的

作品の作業コピーをブラウザーの OPFS に置き、SB3 の入出力と GitHub 同期で使える保存方式を追加する。既存の作品フォルダ版（File System Access・ローカル Git）は残し、設定で選べるようにする。

## 2. 決定事項

| # | 決定 |
|---|---|
| D1 | OPFS 版は新規パッケージとして作る。既存の作品フォルダ機能は置き換えない |
| D2 | 既存の File System Access 版（作品フォルダ・ローカル Git）を残す |
| D3 | 1 作品 1 リポジトリ |
| D4 | 保存方式（OPFS 版／フォルダ版）は設定で選べる |

D2 の理由: OPFS だけでは AI エージェントが作品ファイルを読めない。エージェントには GitHub リポジトリを clone して渡す運用になるため、OPFS 版でも作品は必ず Git リポジトリとして扱う。

## 3. 仮定（未承認）

| # | 仮定 | 違う場合 |
|---|---|---|
| A1 | 保存方式の設定は作品ごとに記録する。新規作品は全体の既定値を使う | 全体で 1 つの設定にする |
| A2 | OPFS 版から GitHub への push は明示操作。自動同期はしない | 自動 push を追加する |
| A3 | 作品の展開形式は sb3-toolchain（現行 0.28.0）が書く作品フォルダ形式 v1 に合わせる（`project.json` とアセット）。形式 v2 は、この新パッケージでは扱わない（読みも書きもしない）。旧作品の変換は sb3-toolchain 側で行う（U5） | 独自形式にする |

## 4. 構成

### 4.1 ストレージ層（OPFS）

- 配置: `turbowarp-plus-projects/<projectId>/`（OPFS のルート直下）
- 作品ごとに `.git/` を持つ作業ツリーとする
- 排他制御: 作品ディレクトリ直下のロックファイル。プロセス起動時に取得し、取得できなければ読み取り専用で開く（既存方針に合わせる）
- 永続化: 起動時に `navigator.storage.persist()` を要求する。拒否された場合は、SB3 書き出しと GitHub push を正式なバックアップとして案内する

### 4.2 Git 層

- 実装候補: isomorphic-git を OPFS 上の `fs` アダプターで使う（要検証: 大きなアセットでの性能、シンボリックリンク非対応の影響）
- 通信: 既存の Git プロキシ（`/v1/git/<owner>/<repo>.git/`）を流用する。認証は既存の短期 Bearer を使う
- 操作: init / add / commit / status / log / diff / fetch / pull / push
- pull は未保存の変更があるときは拒否する

### 4.3 SB3 入出力

- 入力: SB3（ZIP）を `unpackSb3` で形式 v1 の作品フォルダに展開し、OPFS に書き込む（`project.json` は整形して差分を読みやすくする）。形式 v2 のフォルダを開いたときは、変換が必要と案内して開かない
- ブロックパレットの状態: 現行の Editor は `.tw-plus/workspace.json`（形式 v1 の作品フォルダ内、SB3 では ZIP エントリ `tw-plus/workspace.json`）に保存する。形式 v2 の `block-palette.json` は旧仕様で、0.26 以降は書かない。新パッケージでは読まず、旧作品は sb3-toolchain の変換で `workspace.json` へ移す（U5）。
- 出力: OPFS の内容から SB3 を生成する。保存形式（`embedded-file` など）は `turbowarp-sb3-save-format` に従う
- 保存先: File System Access が使えれば保存ダイアログ、使えなければダウンロード

### 4.4 GitHub 1 作品 1 リポジトリ

- 新規作品: 作成時に GitHub リポジトリを作る（または既存リポジトリを選ぶ）。作品と remote を 1 対 1 に紐づける
- 紐づけ情報は作品ディレクトリ内の設定ファイルに持つ（リポジトリ URL のみ。トークンは持たない）
- リポジトリの作成は既存の Git 層（GitHub App）の権限範囲に収まるか要確認

### 4.5 保存方式の切り替え

- 設定値: `storageMode = "opfs" | "folder"`（A1 に従い作品単位で記録）
- 既存の作品フォルダ版との切り替えは、作品の再読込時にのみ行う（実行中の切り替えはしない）
- フォルダ版から OPFS 版への移行は、SB3 書き出し→OPFS 取り込みで行う。自動移行はしない

## 5. エージェント連携

- OPFS 版の作品は、push 済みの GitHub リポジトリが正本として見える状態にする
- エージェントは clone して作業する。OPFS 版の作業コピーを直接読む経路は作らない
- 未 push の変更がある場合、Editor は「エージェントに見えていない変更がある」ことを表示する

## 6. 境界とパッケージ依存

- 新パッケージは GUI・scratch-gui の部品を import しない
- GUI 側との接続は port（型と約束は MPL 側で定義）で行い、GPL 側が呼び出すか実装を差し込む
- fork は family パッケージに直接依存しない（差し込み口とフックのみ）
- 本リポジトリは保存方式の設定 UI、port の登録、結線テストだけを持つ

## 7. 検証計画（案）

1. 単体: OPFS アダプターの読み書き、ロックファイル、`project.json` 整形の往復
2. 結線: SB3 → OPFS → SB3 の往復で内容が一致すること（既存の保存再読込テストの形式に合わせる）
3. Git: init → commit → push → 別クローンで pull して内容が一致すること（テスト用リポジトリを使う）
4. 設定: 作品ごとの保存方式が再読込後も保たれること、フォルダ版の既存動作が変わらないこと
5. 失敗系: 未保存変更がある pull の拒否、ロック取得失敗時の読み取り専用、persist 拒否時の案内

## 8. 未決事項

- U1: isomorphic-git の性能検証（大きな SB3 での commit 時間）
- U2: GitHub リポジトリ作成を Editor から行うか、既存リポジトリの選択のみにするか
- U3: 既存の作品フォルダ版のローカル Git と、OPFS 版の Git 操作をどこまで共通化するか
- U4: 作品ディレクトリ内の設定ファイル名と形式
- U5: 形式 v2 の読み取りを廃止する時期と方法。推奨は段階的な廃止：(1) 新規は書かない（済）、(2) v2 を検出したら変換コマンドを案内する、(3) 一括変換で v1＋`workspace.json` へ移す、(4) 利用実績を確認してから読み取りを削除する。sb3-toolchain 側の変更であり、本草案の範囲外
