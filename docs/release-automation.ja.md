# plus-family の自動化案

[手順書](release-executor.md)を広げた実装です。新しい経路は明示して使います。

## 使い方

### 一括化

```sh
npm run release:chain -- sb3-toolchain --workspace /tmp/chain-01
```

snapshot・plan・preview を保存します。既存の作業場所は使いません。
`--data` で収集済みの情報、`--config` で例外を使えます。

### 候補

```sh
npm run release -- --plan /tmp/chain-01/plan.json \
  --resolved /tmp/chain-01/preview.json --workspace /tmp/chain-01/execution --prepare
```

公開せず、実行できる対象を準備します。
`candidates.json` で差分・文面・候補 SHA を確認できます。
承認後は、その digest を使います。

```sh
npm run release -- --plan /tmp/chain-01/plan.json \
  --resolved /tmp/chain-01/preview.json --workspace /tmp/chain-01/execution \
  --candidates /tmp/chain-01/execution/candidates.json --execute --confirm <digest>
```

終わったら再び `--prepare` で次の対象へ進みます。
候補を作った workspace では、従来の計画 digest で承認を省略できません。

### AI 分担

```sh
npm run release:tasks -- --plan /tmp/chain-01/plan.json \
  --snapshot /tmp/chain-01/snapshot.json --repos-dir /tmp/chain-01/sources \
  --output /tmp/tasks-01
```

独立した checkout と作業ファイルを作ります。
`--worker` にコマンド配列の JSON を渡すと、3件ずつ動かせます。
worker は作業ファイルと結果ファイルを引数として受け取ります。
結果はレビュー待ちです。公開や `reviewedRepositories` の変更には使いません。
これは OS の sandbox ではないため、信頼できる worker だけを指定します。

### 状態と反映

```sh
npm run release:status -- --plan /tmp/chain-01/plan.json --workspace /tmp/chain-01/execution
npm run release:finish -- --plan /tmp/chain-01/plan.json \
  --resolved /tmp/chain-01/preview.json --workspace /tmp/chain-01/execution \
  --execute --confirm <計画digest>
```

反映には全対象の完了と、Pages 起動の承認が必要です。
未完了なら同じコマンドで確認し直します。dispatch は繰り返しません。
失敗した run を再実行する場合は、記録を確認してから行います。
Pages の新しい input が main に入ってから使います。

## 制限

作業場所をまたぐ lock は、この checkout の共通ディレクトリに置きます。
別のツール checkout を使う場合は共通の場所を指定してください。
AI worker の自動修復の採用と、起点の自動推薦はまだありません。
検証済み候補が変わった場合は作り直します。

まずは **収集から dry-run までをまとめ、候補を作れるようにする** のがよさそうです。
そのうえで、AI に調査や修正を分担させます。公開は1つの実行器に任せます。

## いまの状態

| 段階 | できていること | 次にできること |
| --- | --- | --- |
| 収集 | 並列で情報を取得する | 対象の漏れや、古い情報を確認する |
| 計画 | 複数起点、DFS、共有依存の重複排除 | 起点の候補と、対象になった理由を出す |
| dry-run | 設定と参照 SHA を固定する | エラーと判断待ちをまとめて出す |
| 準備 | 依存・版・生成物を更新し検証する | 公開前に止めて、差分を確認する |
| 実行 | 依存先を待ち、独立対象を並列実行する | 別 workspace の重複作業を防ぐ |
| 再開 | `state.json` から続ける | 失敗の種類と次の手順を出す |
| 反映 | Pages が生成・配信する | リリース結果との照合までまとめる |

従来の dry-run は計画の確認です。候補の検証は `--prepare` で行います。

## スクリプトへ任せる部分

### 1. 入口をまとめる

`release:chain` を作り、収集 → 起点選択 → 計画 → checkout → dry-run をまとめます。
既存処理を呼び出す形にし、判定を二重にしません。

毎回新しい作業場所を使い、snapshot・計画・preview を一緒に保存します。
失敗して空になったファイルを、前回の成功と取り違えないようにします。

起点は候補として示します。古い依存だけでなく、未公開変更や準備済み版も見ます。
候補を機械的にすべて選ぶと、意図しない公開が増えるためです。

### 2. 候補を作る

`prepare` を加え、外部へ書き込まずに差分と検証結果を作ります。
上流の予定版が未公開なら、その下流の install は待ちます。
そのため、全 repo の候補を最初に完成させる方式にはしません。上流の公開を確認できた対象をまとめます。

候補には、SHA・更新前後の版・差分・検証結果・PR の文面を残します。
現在は文面を公開直前に作るため、ここへ移します。

承認後は同じ候補を使います。作り直した場合は、差分と検証を確認し直します。
新しい digest だけでは承認になりません。
承認する内容に、対象 repo・head/base・候補の差分・公開文面を含めます。

### 3. 再開をわかりやすくする

`status` で、完了・失敗・依存待ち・判断待ちを一覧にします。
エラーは文章に加えて種類を持たせます。

| 種類 | 次の手順 |
| --- | --- |
| 通信・反映待ち | 状態を照合してから、回数を限って再試行する |
| 検証失敗 | 候補を保持し、原因を調べる |
| main・契約の変更 | 再計画し、前の実行と比べる |
| 公開済み・既存タグ | 公開元を照合する。上書きしない |
| peer・Git・RC | 根拠を集め、判断待ちにする |

### 4. 最後をまとめる

全対象の結果を照合し、承認範囲に含まれる場合に Pages を起動します。
run ID を保存し、再開しても二重起動しないようにします。

成功したかだけでなく、公開した版が収集結果とページに現れたかを確認します。
別の更新もあり得るので、全件の完全一致ではなく今回の対象を照合します。

## AI に任せる部分

AI は、機械的な更新で済まないところを担当します。
親が範囲を決め、担当ごとに独立した checkout を渡します。

| 担当 | 入力 | 出力 |
| --- | --- | --- |
| repo の調査 | 固定 SHA、既存手順 | 準備・検証の根拠、不足 |
| 互換性の調査 | 旧版・新版、利用箇所 | peer・Git・RC の判断材料 |
| 失敗の調査 | 候補、エラー、ログ | 原因、最小修正、検証 |
| 結果の確認 | 公開記録、計画 | 不一致と報告の草案 |

たとえば A の下に B と C があり、その両方を D が使う場合は、
B と C を並列にできます。D は両方の完了後です。

AI の結果には、SHA・変更ファイル・実行した検証を含めます。
検証していない部分や、ユーザーの判断が必要な部分も明記します。

たとえば「sb3-toolchain の変更を使う側へ伝える候補を用意して」と頼めるようにします。
親が起点と計画を確かめ、子に調査を渡し、結果をまとめます。
その後は、依存先が公開済みの対象から候補を作ります。
必要な承認を受けて公開し、次の対象へ進みます。

## 並列化のルール

repo ごとに担当を決め、同時編集を避けます。
実行器と AI が同じ場所を触らないようにします。

現在のスケジューラは、`dependencyUpdates` を使っています。
AI の調査も含めるなら、依存グラフを使って全体を判断する必要があります。

担当ごとに `release` を起動せず、公開は1つにまとめます。
そのために、repo・版・操作ごとの所有者を管理します。

最初は2〜3件で試します。API、CPU、ディスク、CI の待ち時間を測ります。
件数を増やすだけでは速くならないことがあります。
AI の枠とビルドの枠も分けます。調査の空きを、重いビルドで埋めないようにします。

## 承認と変更

AI が互換と考えても、`reviewedRepositories` を自動で増やしません。
判断材料を返し、確認されたものだけを使います。

公開内容が変わった場合は、候補を作り直します。
それ以外は、承認された操作列の中で進めます。

途中で直す場合も、元の workspace は保持します。
修正後の候補を別の場所で検証し、必要なら再計画します。

## 進め方

小さく分けます。

| 順 | 内容 | 依存 | 確認すること |
| --- | --- | --- | --- |
| 1 | 入口と保存をまとめる | なし | 失敗した出力を成功扱いせず、公開しない |
| 2 | 候補と承認を分ける | 1 | 承認した候補と公開した内容が一致する |
| 3 | 所有者を管理する | 2 | 別 workspace でも同じ repo を同時に更新しない |
| 4 | AI を分担させる | 3 | 子の失敗や重複回答があっても状態が壊れない |
| 5 | 再開を助ける | 4 | 修正後に変更が必要な範囲だけを検証する |
| 6 | Pages と結果照合 | 3 | 同じ run を待ち、公開結果を照合する |

受け入れ基準は、二重公開がないこと、依存先の完了前に進まないこと、
再開で同じ検証を無条件に繰り返さないこと、候補が変われば確認し直すことです。
検証結果は入力 SHA・依存・環境が一致している場合に使います。成功した記録がなければ再検証します。
安定版のリリースでは、各 repo が求める全体検証も維持します。

新しい経路は既定OFFで入れます。戻すときは既存経路を使います。
公開済みの版やタグは消さず、必要なら別番号で直します。

実装は [#126](https://github.com/kubohiroya/turbowarp-plus-packages/issues/126) で追っています。
